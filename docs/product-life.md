# 产品规划：个人生活大一统 Agent

> 2026-11-23。定位第三次修订：从"个人消息数据层"，到"个人工作平台"，再到**个人生活大一统的 Agent**。
>
> 和 Persona 等竞品相比，我们更重要的差异是**生活**能力：它们解决"让 Agent 帮我干活"，我们解决"我生活里的一切信息在一个地方，Agent 帮我打理"。工作编排是其中一块，不是全部。

## 1. 定位

**life-agent 把你生活里散落各处的信息收进一个中心：消息、账单、快递、行程、日程、健康、家里的设备。它自动整理成"今天要关心什么"，并让 Agent 帮你处理。**

三层结构：

```
 ┌────────────────────────── 场景（你直接用的） ──────────────────────────┐
 │ 今天简报 · 需要看 · 快递取件 · 账单与还款 · 行程 · 订阅续费 · 报销 · 告警 │
 └───────────────────────────────▲─────────────────────────────────────┘
                                 │ 抽取（规则 + LLM）：从原始记录里识别出"生活对象"
 ┌───────────────────────────────┴─────────────────────────────────────┐
 │ 生活对象：消息 · 快递 · 账单/交易 · 行程 · 日程 · 订阅 · 发票 · 设备事件 │
 └───────────────────────────────▲─────────────────────────────────────┘
                                 │ 数据源（连接器，跑在 hub 或各台机器的 node 上）
 ┌───────────────────────────────┴─────────────────────────────────────┐
 │ IM · 邮件 · 短信 · 日历 · 支付账单 · 健康 · 位置 · 智能家居 · 投资 · …  │
 └─────────────────────────────────────────────────────────────────────┘
```

同一份原始数据可以长出多个生活对象。比如一封信用卡账单邮件，在收件箱里是一封邮件，在"账单"里是一笔待还款，在"今天"里是一句"周五前还 3,280 元"。

## 3. 数据源目录

原则：
- **能读就读全**：消息类尽量拿到完整历史，而不是只拿到发给机器人的。
- **风险写清楚**：涉及平台条款或封号风险的方式，默认关闭，并在文档里写明。
- **个人数据走全量汇总，公司数据只汇总"信号"**（见竞品分析第 6 节）。

### 3.1 消息

| 数据源 | 方式 | 能拿到什么 | 风险 / 限制 | 状态 |
|---|---|---|---|---|
| 微信 | 读已解密的本地库（只读） | 全部聊天记录 | 解密工具自选，见 connectors.md | ✅ |
| 飞书 | lark-cli 以本人身份 | 全部会话 | 公司数据，合规见竞品分析第 6 节 | ✅ |
| QQ | NapCat（OneBot v11） | 全部私聊、群聊（实时） | 非官方客户端，有风控风险；挤掉桌面 QQ | ✅ |
| 邮件 | IMAP，多账号 | 全部邮件 | Outlook 需要 OAuth（待做） | ✅ |
| **Discord** | **Bot**（Gateway + REST） | Bot 所在服务器里有权限的频道，**包括历史消息**；发给 Bot 的私信 | 读不到你个人号和朋友的私信。用户 token（selfbot）违反 Discord 条款，**不做**。个人私信历史可后续通过 Discord 官方"数据包导出"导入 | 本轮实现 |
| Telegram | 用户身份客户端（MTProto） | 全部会话 | 官方允许 | 规划 |
| iMessage / 短信 | 读 Mac 上的 `chat.db`（需要完全磁盘访问权限） | iMessage；打开 iPhone 的"短信转发"后**还有全部短信** | 只读；只能在 Mac 上 | 规划（生活场景的关键数据源） |
| WhatsApp | whatsmeow | 全部会话 | 非官方协议，有封号风险 | 规划 |
| Slack | 用户 token | 全部会话 | 看工作区策略 | 规划 |
| 钉钉 / 企业微信 | 官方开放平台 | 有限（多为机器人或管理员能力） | 个人消息能力受限 | 待评估 |

## 4. 生活便捷场景

| # | 场景 | 用到的数据源 | 怎么做 |
|---|---|---|---|
| 1 | **快递取件码聚合**：所有取件码一张卡片，取完划掉 | 短信 | 规则抽取（驿站、快递柜的短信格式比较固定） |
| 2 | **今天简报**：早上一张卡片看完天气、日程、需要看、待取快递、待还款、出行 | 全部 | 汇总各模块，可让 Agent 写成一段话 |
| 3 | **账单与还款提醒**：信用卡账单日、还款日、金额 | 邮件、短信 | 规则 + LLM 抽取，到期前提醒 |
| 4 | **出行助手**：航班、火车自动进日程，出发前提醒天气和出门时间 | 短信、邮件、天气 | 抽取行程对象 → 日程 |
| 5 | **订阅续费提醒**：识别各种自动续费，续费前 3 天提醒 | 邮件收据 | 抽取订阅对象 |
| 6 | **报销助手**：自动收集电子发票，月底生成报销清单 | 邮件附件 | 识别发票 PDF，交给 Agent 整理 |
| 7 | **自动记账**：动账短信、支付账单导入，自动分类 | 短信、账单导入 | 规则 + LLM 分类 |
| 8 | **家里告警**：门没关、漏水、摄像头异常进入告警栏 | Home Assistant | 设备事件 → 告警 |
| 9 | **生日 / 纪念日提醒** | 通讯录、日历 | 规划 |
| 10 | **日记草稿**：每晚根据足迹、消息、日程生成一份草稿 | 位置、消息、日程 | Agent 生成，你修改 |
| 11 | **验证码**：最新验证码一键复制，用完即焚 | 短信 | 只在内存里展示，不入库 |

## 5. 架构上要改的

1. **连接器从"只产生消息"扩展为"产生记录"**：除了消息，还有交易、日程事件、设备事件、文件等。数据层增加通用的 `records` 表，保留原始内容。
2. **抽取器（extractor）**：把原始记录识别成生活对象（快递、账单、行程、订阅、发票）。先用规则，再用 LLM 兜底；每个对象都能追溯到它来自哪条原始记录。
3. **生活对象的统一模型**：类型、关键字段（金额、时间、地点、单号）、状态（待处理 / 已完成）、来源记录。和消息一样带变更序号，多端同步直接复用。
4. **"今天"是一个聚合视图**，不单独存数据。
5. **敏感数据分级**：验证码只放内存，不落库；公司数据只存元数据；健康和位置可以单独加密。

## 6. 和 Persona 的对照（2026-11-23）

Persona 的生活能力集中在**手机自带的数据**：健康、日历、通讯录、HomeKit，加上早报和 Watch 录音回顾，都由原生 App 读取。它**没有**快递、账单、记账、出行、生活订阅、报销，也没有微信和 QQ 的聊天记录。详见竞品分析 2.5 节。

所以我们的打法是：
- **先做散落在短信和邮件里的生活事务**：这是 Persona 的空白，也是数据源的独占优势（微信、QQ、本人身份的飞书）。
- **手机原生数据**（健康、日历、HomeKit）后做，因为 Persona 已经做得很深；做的时候借鉴它的敏感信息分级和"不存轨迹"的选项。
- **它的北极星"每天打扰几次"值得照搬**：生活助手越安静越好，推送和"需要看"都要计数。

## 7. 优先级建议

1. **Discord**（本轮）
2. **iMessage / 短信**：一个数据源解锁快递、验证码、动账、行程四个场景，性价比最高。
3. **抽取器框架 + 快递取件码 + 今天简报**：第一个能天天用的生活场景。
4. 邮件抽取：账单、订阅、发票、行程。
5. 日历、天气、Home Assistant。
6. 其余数据源按需补齐。
